Last year I wrote about [design systems for bots](https://www.petrilahdelma.com/writing/design-systems-for-bots): UI contracts that agents cannot misinterpret. The argument was simple — if agents touch your product, vague systems create broken UI at machine speed.

Since then I have watched teams run the experiment for real. The pattern is consistent. The agent ships fast. The first draft looks plausible. Then someone opens the diff and finds the same three failures: wrong action hierarchy, raw values instead of semantic tokens, and a component choice that made sense in Storybook but not in the flow.

AI did not expose a new problem. It removed the slack that used to hide it.

If you read [From Tokens to Thinking Systems](/blog/from-tokens-to-thinking-systems-making-ai-native-design-systems-actually-work), that piece asked what AI-native design systems must encode. [Figma MCP](/blog/figma-mcp-design-systems) showed one tool surface. **This five-part series asks how teams operate those systems** when agents, linters, and humans share the same repo — with evidence that fails in CI, not in Slack.

## The wrong question

Teams still ask whether a design system is worth the effort now that models can generate screens. That is the wrong question.

The right question: **can your system be operated by the new builders in the workflow?**

Those builders are not only designers and engineers anymore. They are coding agents, Figma MCP clients, Storybook runners, token linters, accessibility scanners, and the orchestration layers that turn written intent into product changes.

A component library tells an agent what pieces exist. It rarely tells the agent how the product thinks. You may expose a `Dialog`, but not the difference between confirmation, destructive commitment, and “this should not be a modal at all.” You may expose a `Button`, but not the rule that a decision region gets one primary action.

If the system is mostly a visual catalogue, AI routes around it. If the system is an operating model, AI can work inside it.

## What “operating model” means in practice

I use operating model to mean the loop that connects intent, rules, output, and evidence:

```txt title="agentic-system-loop.txt"
Intent -> Rules -> Output -> Evidence -> Better rules
```

Intent is the product decision: “user deletes workspace,” “show billing error with recovery,” “settings page for a power user.” Rules encode what that means in system terms — which pattern, which component variants, which tokens, which forbidden combinations. Output is the generated or hand-built UI. Evidence is what proves the output still matches the rules: stories, tests, contrast checks, contract validation, review notes.

Without the loop, you get a library. With the loop, you get something agents and humans can repeat under pressure.

Operating rules belong in [component contracts](/blog/component-contracts-are-where-taste-becomes-infrastructure) — not as documentation prose, but as structure an agent or validator can use: allowed use, forbidden use, required evidence, review triggers. We are migrating toward semantic fields like `forbiddenUse` and action hierarchy; today’s shipped checks focus on structural alignment (props, stories, a11y flags). Both layers matter. The loop only works when you know which is enforced now and which is next.

## What agents inherit (and what they do not)

When humans use a design system, they carry missing context. They remember which component is technically available but politically deprecated. They know one product area runs dense tables while another stays marketing-sparse. They infer that a “simple” error still needs recovery copy because support will absorb the confusion otherwise.

Agents inherit none of that unless you encode it.

They read files, names, exports, stories, tests, and comments. If contradictions exist, they reproduce them. If the easiest example to copy is stale, stale becomes the default. I have seen an agent pull the first Storybook story for a card — the one with hardcoded padding from 2022 — because nothing in the contract said that story was legacy.

That is why agentic design systems are less about “adding AI features” and more about tightening the boundary between intent and execution. The system must say what something means, when to use it, what it must never do, and how the team proves it still works.

## Governance as throughput, not ceremony

Many teams hear governance and imagine committees. In agentic workflows, governance is a throughput tool. It prevents every sprint from rediscovering the same decisions.

Useful review questions shift:

- Which contract controlled this change?
- Which example did the agent copy?
- Which checks produced evidence?
- Which decisions still required human taste?

Under production pressure, humans and agents both reach for the nearest pattern. If the nearest pattern is explicit and validated, the system compounds. If it is stale or ambiguous, drift compounds faster than before — because now you have more authors.

Token enforcement is a good early win. In our repo we use Stylelint with declaration strictness (`stylelint-declaration-strict-value`) so raw values fail instead of slipping through review. That is operating model, not documentation.

> **Shipped today vs. target schema**  
> Our repo runs `npm run validate:components` against 127 `.contract.json` files — props aligned with CVA, required Storybook stories, a11y flags, token lists. Semantic rules (forbidden combinations, action hierarchy) are the **next layer** we encode in docs and migrate into failing checks. When later posts show richer JSON, read the label: **v1 structural** is CI today; **v2 semantic** is design direction.

## A maturity test that still holds

In [design systems for bots](https://www.petrilahdelma.com/writing/design-systems-for-bots) I framed three levels:

1. **Readability** — can an agent find the right component from docs alone?
2. **Executability** — can you validate generated UI mechanically?
3. **Survivability** — can you change internals without breaking consumers?

Most teams claiming “AI-ready” are still arguing about level 1. Level 2 is where agentic work becomes safe: token linting, prop constraints, accessibility checks, contract validation, visual smoke tests. If you fail level 2, agents will still generate UI — you will debug it in production.

Ask honestly:

- Can a new contributor ship a compliant page without ten Slack questions?
- Can an agent produce a first draft with the right components, tokens, and patterns?
- Can validation separate a harmless detail from a broken contract?
- Can the team see what is stable, experimental, deprecated, or unsafe for generation?

Weak answers mean more components will not help. More operational clarity will.
