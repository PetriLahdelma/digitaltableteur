DesignOps solved a human coordination problem: how design teams work with clarity, consistency, and organizational trust across rituals, libraries, critiques, research repositories, and handoffs to engineering.

That work still matters. The environment changed.

Agents now show up as implementers, reviewers, test writers, documentation assistants, and sometimes autonomous editors in the repo. They do not replace DesignOps. They extend it.

I use **AgentOps** here as internal vocabulary — not a new department, but **DesignOps plus agent guardrails**: making automated work reliable enough to use on real product systems. DesignOps made collaboration legible. AgentOps makes automated collaboration inspectable.

## The design-system lead becomes a context operator

In classic design-system work, context lived in people. The lead knew why a component exists. A senior designer remembered why a pattern failed last quarter. The frontend architect knew which API was stable and which was legacy-only.

Agents need that context written, structured, and retrievable.

The expanded job is **curating the information environment agents use**:

- Which documents are authoritative?
- Which examples should agents copy?
- Which patterns are safe for generation?
- Which rules are hard constraints vs. guidance?
- Which decisions require human taste?

Bad context produces bad automation at scale. Good context compounds.

## AgentOps is not “let the AI do it”

The immature version: ask for a screen, receive a screen, merge the screen, discover the problems in QA.

AgentOps asks for inspectability:

- System rules known before editing
- Source of truth explicit
- File boundaries enforced
- Validation commands run before review
- Mechanical vs. judgment changes separated

If an agent changes a component, the team should see **why**, against **which contract**, with **which tests**, under **which review rule**. Otherwise the workflow is automated ambiguity.

### Evidence beats invented scores

We do not run a numeric eval pipeline yet. We do run mechanical gates. Example from our repo: an agent-assisted PR renamed a Storybook story without updating `Button.contract.json`. `npm run validate:components -- --component Button` failed in CI — required story missing, contract drift caught before a human opened the diff.

That is AgentOps at v1: **failing commands as evaluation**, not Slack vibes or fabricated 0.9 scores. Numeric rubrics come later, when you have enough labeled failures to score against.

## Responsibilities (extensions, not replacements)

| Responsibility | What it means |
|----------------|---------------|
| **Contract design** | Repeatable quality encoded as rules, not slides |
| **Context curation** | Right examples promoted; stale ones demoted |
| **Workflow design** | Harness boundaries for common agent tasks |
| **Evaluation** | Same failures become rules, not repeat review comments |
| **Escalation design** | Brand, a11y exceptions, destructive flows, legal copy → human |

Design-system practitioners already translate between product intent, brand, accessibility, APIs, documentation, and adoption politics. Agents make coherent systems spread coherence faster — and vague systems spread vagueness faster.

## When AgentOps is not worth the tax

Skip or defer this layer when agents are not in your delivery loop, when you cannot maintain contracts after launch, or when a strong `AGENTS.md` and Storybook cover 80% of your risk for the next two quarters.

Maintenance cost is real: 127 contracts only help if someone updates them when props change. Org politics matter too — engineering may route agents around the design system unless the harness lives in the repo they actually use.

## A cadence that fits a working squad

Not a ceremonial program — a learning loop:

- **Daily** — did agent work pass the harness?
- **Weekly** — which failures repeated?
- **Monthly** — turn repeats into contracts, examples, or skills
- **Quarterly** — is the system safer than last quarter?

If the same mistake appears three times, it should stop being a review comment and become a rule, example, contract, or check.

## Closing

Craft moves upstream. Instead of only designing the button, you design the rules that keep the next thousand decisions coherent.

The question is not whether teams will use agents. They will. The question is whether work happens **inside** the system or **around** it — with context, evidence, and trust designed as deliberately as the components themselves.
