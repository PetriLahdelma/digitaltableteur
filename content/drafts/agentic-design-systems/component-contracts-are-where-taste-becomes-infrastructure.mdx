If you read [From Tokens to Thinking Systems](/blog/from-tokens-to-thinking-systems-making-ai-native-design-systems-actually-work), you already know the theory: LLMs follow rules when rules are explicit, scoped, and validated. **This post is where theory becomes CI** — how judgment becomes infrastructure without flattening craft.

A senior designer can glance at a screen and say: hierarchy is noisy, spacing belongs to three different systems, the primary action is fighting the destructive one, the empty state is performing optimism instead of helping.

That judgment is taste. Taste trapped in one person’s head is not a design system. It is a bottleneck.

**A contract is taste with handles:** precise enough for agents, validators, and new teammates to hold without guessing.

This builds on [design systems for bots](https://www.petrilahdelma.com/writing/design-systems-for-bots) and the [operating model loop](/blog/agentic-design-systems-need-operating-models-not-more-components): if you cannot validate generated UI mechanically, you will debug it in production.

## Documentation explains. Contracts constrain.

Most component docs describe purpose, props, variants, examples, dos and don’ts. Useful for humans. Insufficient for agents.

Agents need constraints: allowed variants, required states, forbidden combinations, deprecated props, accessibility guarantees, lifecycle status, and what must exist in Storybook before a component is “stable.”

### What we ship today (v1 structural)

Our repo has 127 `.contract.json` files. Here is a real excerpt from `Button.contract.json` — what `npm run validate:components` actually checks against:

```json title="Button.contract.json (shipped)"
{
  "name": "Button",
  "tier": "molecule",
  "status": "beta",
  "requiredStories": ["Default", "Playground", "Example", "ForcedColors"],
  "a11y": {
    "keyboard": ["Enter", "Space"],
    "ariaRequirements": ["accessible name", "aria-busy when loading", "disabled state"],
    "reviewed": true,
    "forcedColorsVerified": true
  },
  "tokens": {
    "colors": ["--color-warning-text", "--color-white"]
  }
}
```

This enforces structural alignment: props match CVA, required stories exist, a11y flags are set, token references are declared. It does **not** yet fail when primary and danger buttons compete in the same action group.

### What we are migrating toward (v2 semantic)

The next layer adds product-level rules — the ones that cause repeat drift:

```json title="Button.pattern-rules.target.json"
{
  "patternRules": {
    "actionHierarchy": {
      "primary": "one per decision region",
      "danger": "destructive or irreversible actions only",
      "tertiary": "supporting actions that must not compete"
    },
    "forbidden": [
      "raw color overrides",
      "icon-only without accessible name",
      "primary and danger competing in the same action group"
    ]
  }
}
```

The schema matters less than the move from recommendation to constraint — and being honest about which layer fails a command today.

I ship contract tooling as open source — [`@petritapanilahdelma/llm-component-contracts`](https://www.npmjs.com/package/@petritapanilahdelma/llm-component-contracts) for versioned JSON schemas, and [`llm-component-cli`](https://www.npmjs.com/package/@petritapanilahdelma/llm-component-cli) for validate, migrate, drift-check, and scaffold. The CLI’s `drift-check` compares schema props to component props and Storybook args. That is v1 infrastructure working: when mismatch fails a command, documentation stops being optional.

## The failure mode of soft rules

Soft rules feel clear until a machine applies them.

- “Use cards for grouped content” — grouped how?
- “Keep primary actions clear” — how many primaries per region?
- “Write concise errors” — concise can still be useless without recovery

Contracts ask for sharper structure:

- A card is allowed when content shares an object boundary, comparison set, or decision context — not whenever layout feels busy.
- A decision region gets one primary action unless a human explicitly approves an exception.
- An error message includes cause, recovery, and next action when the user can act.

Not every design decision should be encoded. Encode the ones that create repeat drift — action hierarchy, token scope, destructive patterns, form validation anatomy, empty states without recovery.

## The anecdote that belongs here

I have watched agents place **primary and danger buttons side by side** in a delete confirmation — technically valid props, contract-violating product design — because nothing in the repo forbade the combination yet.

That is the v2 problem: structural contracts pass, product judgment fails. Contracts become shared memory that does not depend on who is in the room — but only when the forbidden combination actually fails a check.

## Contracts improve human review

Good contracts do not flatten judgment. They protect it.

When validation catches wrong token tier, missing required story, invalid prop combination, or broken accessibility expectation, review stops wasting time on preventable drift. Conversation moves to what still requires taste: fit to user goal, cognitive load, whether an exception is worth the complexity.

```txt title="review-flow.txt"
Proposed change
  -> contract checks catch mechanical drift
  -> evidence attached to review
  -> humans spend attention on judgment
```

## Connect contracts to checks that fail

A contract nobody validates is another doc.

Our validator lives in `scripts/design-system/validate-components.ts` — not pseudocode. Typical checks:

- Props and variants align with the contract and CVA definition
- Required Storybook stories exist
- Token references match declared scopes
- A11y review flags are set before promotion

In practice: `npm run validate:components`, axe in CI, Stylelint with token rules, drift reports from `llm-component-cli`. Uncomfortable at first — then faster, because debates shift from “did we follow the doc?” to “is this exception justified?”

## What to encode (and what to leave human)

**Encode:** token scopes, variant rules, state models, accessibility guarantees, composition anti-patterns, lifecycle stages, required stories, review triggers.

**Leave human:** proportion, brand warmth, narrative timing, emotional fit, the sense that something is technically correct but wrong for the moment.

The strongest systems do not automate taste. They protect the conditions where taste is applied at the right altitude.
