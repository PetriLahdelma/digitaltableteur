Most agentic design-system conversations start with model choice. That is rarely where teams lose.

When I [connected Figma’s MCP server to a live design system](/blog/figma-mcp-design-systems), the interesting part was not the model. It was the metadata: intent, variant logic, and token semantics embedded where the tool could read them. Swap the IDE, keep the [operating model](/blog/agentic-design-systems-need-operating-models-not-more-components), and the workflow still works. Swap the structure, keep the IDE, and you get impressive demos followed by unreviewable diffs.

For design systems, agentic maturity starts when teams separate three things that are usually conflated:

**Tools** — where work happens.  
**Harnesses** — how work stays safe.  
**Skills** — what valuable work becomes repeatable.

## Tools are the workspace

Tools expose surfaces: files, components, diffs, previews, logs, tasks.

Figma, Storybook, GitHub, Cursor, Claude Code, visual regression runners, and MCP integrations all belong here. Good tools reduce context switching and make state recoverable. Bad tools hide state until something breaks in CI.

Tools do not create discipline by themselves. Storybook does not guarantee component maturity. Figma variables do not guarantee token discipline. A coding agent in a repo does not guarantee product coherence.

The tool gives the system a place to act. The harness defines how action is allowed to proceed.

## Harnesses are the operating model

A harness answers questions agents will not infer reliably:

- Which files are authoritative?
- What context must be read before editing?
- Which paths are out of scope?
- Which commands prove safety?
- When must a human review judgment, not mechanics?

Without a harness, teams collect agent wins and production surprises in equal measure. With one, ambiguous intent becomes reviewable work.

We do not ship a single `agent-harness.yml` file. The harness is **distributed** — `AGENTS.md`, `docs/LLM_COMPONENT_GENERATION_RULES.md`, per-component `.contract.json` files, and verification scripts. The YAML below is **illustrative**: the shape those pieces take when you compile them for one component edit.

```yaml title="agent-harness.example.yml"
# Illustrative — not a file in our repo; pattern encoded across AGENTS.md + contracts + CI
scope:
  allowed_paths:
    - nextjs-app/shared/components/Button/**
  blocked_paths:
    - nextjs-app/shared/styles/variables.css

required_context:
  - docs/LLM_COMPONENT_GENERATION_RULES.md
  - Button.contract.json
  - Button.stories.tsx

verification:
  - npm run typecheck
  - npm run validate:components -- --component Button
  - npm run test -- Button

human_review:
  required_when:
    - variant taxonomy changes
    - accessibility exception requested
    - destructive action pattern changes
```

Notice what is missing: model names, prompt poetry, brand adjectives. A harness is operational, not inspirational.

[Project Spine](https://projectspine.dev) packages briefs, repos, and tokens into agent-native context bundles — a different packaging of the same insight: **agents need curated context, not the entire monorepo.**

## Skills are repeatable capabilities

Skills are named playbooks inside the harness. Not “be helpful with components.” Specific jobs with inputs, outputs, boundaries, and exit criteria.

Useful design-system skills:

- Audit a component for token drift
- Generate a Storybook state matrix from a contract
- Compare Figma variant sets to React props
- Draft MDX usage guidance from `Component.spec.md`
- Promote a component from alpha to beta with checklist evidence
- Prepare a deprecation migration note

If a task happens every sprint, it should not depend on whoever is online that day.

```txt title="capability-stack.txt"
Tool surface
  -> Harness boundary
    -> Skill execution
      -> Evidence
        -> Reviewable change
```

On [digitaltableteur.com](https://www.digitaltableteur.com) we publish `dt-*` agent skills as machine-readable `SKILL.md` playbooks — versioned like code, indexed at [/.well-known/agent-skills/](https://www.digitaltableteur.com/.well-known/agent-skills/index.json). That is skills as infrastructure: the same capability available to humans and agents.

A mature skill names inputs, reads, writes, and exit criteria. We are moving toward JSON skill contracts; today the source of truth is markdown with front matter. Target shape:

```json title="skill.contract.target.json"
{
  "name": "component-a11y-pass",
  "input": ["componentName", "contractPath", "storyPath"],
  "reads": ["contract", "stories", "tests", "mdx"],
  "writes": ["test updates", "mdx acceptance criteria"],
  "mustNotWrite": ["global tokens", "unrelated components"],
  "exitCriteria": [
    "axe expectations documented",
    "keyboard behavior covered",
    "manual AT gaps listed honestly"
  ]
}
```

## Diagnose before you buy another tool

When tools, harnesses, and skills blur together, teams fix the wrong layer.

| Symptom | Often misdiagnosed as | May actually be |
|--------|------------------------|-----------------|
| Inconsistent generated UI | “Need a better model” | Weak contracts and examples |
| Wrong button variant | “Prompt issue” | Missing action hierarchy in contract |
| Slow reviews | “Need fewer approvers” | Mechanical checks not automated |
| Generic output | “Model too shallow” | Skill lacks product-specific constraints |

Example: “The agent used the wrong button variant.”

That can be a [contract problem](/blog/component-contracts-are-where-taste-becomes-infrastructure) — hierarchy never defined. A skill problem — no repeatable “choose action pattern for context” playbook. A harness problem — validation never ran before handoff. Rarely is it solved by switching chat clients.

## A practical stack map

Before adding tooling, draw three columns:

**Tools** — make work visible (Figma MCP, Storybook, GitHub, CI).  
**Harnesses** — define boundaries (`LLM_COMPONENT_GENERATION_RULES.md`, allowed paths, verification commands).  
**Skills** — encode repeatability (audit, scaffold, migrate, a11y pass, contract sync).

The tool stack can vary week to week. Invest first in harness clarity — that is the layer agents actually inherit.
