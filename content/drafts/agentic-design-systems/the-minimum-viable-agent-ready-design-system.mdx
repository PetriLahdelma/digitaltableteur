Not every team needs a cathedral.

Some hear “design system” and picture governance councils, forty component owners, and a documentation site with its own roadmap. That is one valid shape. It is not the only one — and it is not where most teams should start if agents are already generating UI in their repos.

The useful target for many squads is a **minimum viable agent-ready design system**: small enough to maintain, strict enough to prevent drift, explicit enough for humans and machines to operate without hallway context.

The alternative to a giant system is not no system. It is a thinner, enforceable one.

## Why “small team magic” stops working

Proximity carries context: who owns brand judgment, which shortcuts are tolerated, which form validation pattern is canonical. Add contractors, parallel squads, coding agents, or a second repo and proximity stops scaling.

Drift shows up quietly:

- Informal button variants
- Empty states with different voice
- Forms validating on different triggers
- Spacing becoming local guesswork
- Dark mode breaking at the edges
- Accessibility arriving in a late audit

None of that requires an enterprise program to fix. All of it requires a real system — just not necessarily a large one.

## Six layers, in order

An agent-ready foundation can start here:

```txt title="minimum-agent-ready-stack.txt"
Semantic tokens
  -> production components
    -> component contracts
      -> pattern recipes
        -> real examples
          -> automated checks
```

**Semantic tokens first.** Agents and developers should reach for `surface`, `text`, `border`, `accent`, `danger`, `focus` — not `gray-800` or `brand-pink-500`. Raw values are implementation details; semantics are product decisions. This is the same API mindset I described in [From Tokens to Thinking Systems](/blog/from-tokens-to-thinking-systems-making-ai-native-design-systems-actually-work).

**Production components next.** Not Figma-only symbols — coded components with stable props, exports, and stories that reflect product reality. Weak code copied by an agent becomes weak product at speed.

**Contracts on serious components.** Start with [structural contracts](/blog/component-contracts-are-where-taste-becomes-infrastructure) — required stories, a11y flags, prop alignment — before semantic rules like forbidden combinations. One validation command in CI beats forty markdown pages.

**Pattern recipes for the gaps.** Forms, settings, tables, permissions, destructive flows, search, empty and error states — the space between atoms.

**Examples that include edge cases.** Loading, empty, denied, long translation, narrow viewport, keyboard-only, high contrast. Agents learn from examples under pressure, not from hero screenshots.

**Checks that fail.** Token lint, typecheck, contract validation, axe, visual smoke. Memory is not a strategy.

That is already a design system — even if you call it a UI foundation or shared interface layer.

## Start where the product already hurts

Avoid opening moves that feel productive but delay enforcement:

- Variant taxonomy debates before contracts exist
- Documentation migration before validation exists
- AI generation before examples exist
- Component count targets

Start where friction is visible:

| Pain | First move |
|------|------------|
| Forms inconsistent | Form recipe: fields, validation, errors, recovery |
| Dashboards drift | Density rules, table toolbar pattern, empty states |
| Agents misuse components | Contracts + stories for top five offenders |
| Accessibility late | Promotion gate: no stable without axe + keyboard coverage |
| Brand dilution | Semantic token scopes + real usage examples |

Grow from repeated product friction, not from an abstract inventory dream.

## Agent-readiness checklist

A small system is agent-ready when it answers these without Slack archaeology:

- **Find** — consistent naming across Figma, code, docs, Storybook
- **Choose** — contract + examples describe intent, not only appearance
- **Generate valid usage** — props, slots, tokens, a11y rules are constrained
- **Detect invalid usage** — one command humans and agents can run
- **Review the right layer** — mechanics automated, judgment human
- **Change safely** — deprecations and migration notes are normal

```json title="minimum-agent-ready-system.json"
{
  "tokens": ["semantic-color", "type-scale", "spacing-scale", "focus"],
  "components": ["Button", "Input", "Select", "Dialog", "Alert", "Card"],
  "patterns": ["Form", "EmptyState", "ErrorState", "TableToolbar"],
  "checks": ["typecheck", "validate:components", "axe", "visual-smoke"],
  "review": {
    "humanRequiredFor": ["new pattern", "breaking change", "a11y exception"]
  }
}
```

Six components with contracts and checks will outperform forty components with markdown only — if someone owns keeping them current.

## Who owns this in a three-person squad?

You do not need a design-system team. You need a **named owner** — often the design-system lead, staff frontend, or the person who already answers “which button do we use?”

Rough split that works:

- **Design** — token semantics, pattern recipes, Storybook examples
- **Engineering** — contracts, validation script, CI gate
- **Shared** — promotion criteria (experimental → beta → stable)

If nobody owns contracts, agents will still generate UI. The system just will not learn from failures.

## A 30–60–90 day path that fits a squad

**Days 1–30 — stop the bleeding**

- Semantic color, spacing, type, focus tokens
- Structural contracts for Button, Input, Dialog, Alert, Card
- One validation command in CI (`validate:components` or equivalent)

**Days 31–60 — make generation safer**

- Form and error-state recipes
- Edge-case Storybook stories for top components
- Token lint (Stylelint strict-value or equivalent)

**Days 61–90 — make adoption repeatable**

- Lifecycle stages: experimental → beta → stable → deprecated
- Contribution rules: what evidence is required to promote
- Migration notes when APIs change

Treat the timeline as a hypothesis, not a guarantee. Squad size and existing debt matter. The point is to ship enforcement before agents outpace your docs.

## When to stop (or never start)

This stack is overkill when:

- You are pre-product-market-fit with throwaway UI
- One person owns all surfaces and will for the next year
- Agents are not touching the repo yet — good `AGENTS.md` + Storybook may be enough for months
- You cannot maintain contracts after the first sprint (unmaintained contracts become lies agents trust)

False confidence is a real risk: green CI with wrong product judgment. Structural validation catches drift in props and stories; it does not replace design review for hierarchy and copy.

**Speed with memory** — when the stack fits, generated output starts closer to acceptable, onboarding shortens, and external contributors plug into boundaries instead of reverse-engineering taste from screenshots.

You do not need the entire enterprise machine before AI becomes useful. You need a system that knows what it is — and proves it.
