# Design System Maturity Model

This public model scores a team across six dimensions. Each dimension is 0-3.

| Dimension | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| Tokens | Unstructured styles | Named tokens exist | Tokens build to code/Figma | Token drift is automatically blocked |
| Components | Ad hoc UI | Shared components exist | Contracts, stories and tests exist | Stable components have ownership, a11y evidence and adoption data |
| Governance | Informal reviews | Contribution rules exist | Release gates and review paths exist | Governance is routine, measured and delegated |
| Adoption | Copy-paste use | Teams know the system | Product teams consume documented APIs | Adoption health is visible by team/product |
| Accessibility | Manual spot checks | Basic axe checks | Stories and pages have a11y gates | Accessibility evidence is captured across themes/states |
| Automation | Manual maintenance | Local scripts exist | Generated artifacts have drift checks | Agents and humans share enforceable workflows |

Score interpretation:

- 0-5: Inventory stage. Stabilise naming, tokens and ownership.
- 6-10: Foundation stage. Add contracts, tests and contribution flow.
- 11-15: Operating stage. Make drift, accessibility and adoption measurable.
- 16-18: Scaling stage. Treat the design system as governed product infrastructure.

Use this model in audits, retainers and case-study rewrites so claims about maturity map to observable evidence.
