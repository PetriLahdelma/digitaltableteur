# Switch

**Status:** beta · **Tier:** atom · **Group:** form

Two-state toggle for settings. Switch differs from Checkbox in semantic
intent — `role="switch"` is announced as "on/off" rather than
"checked/unchecked", and the visual idiom is a sliding thumb rather than
a tick box. Loading and disabled states are first-class; an optional
helper text slot pairs with the label.

## In use

Used in settings panels (theme toggle, motion preference toggle), the
chat widget's notification preference, and consent toggles in the cookie
consent flow. The **Example** story shows the labelled controlled
composition with a helper line.

Two compositions worth cribbing:

- **Setting toggle with helper.** Pass `label` and `helperText`. The
  switch becomes the entire labelled atom; the helper carries the
  explanation. The label can wrap or float depending on `labelPlacement`
  (`right` default, `left`, or `top`).
- **Async setting.** When the change requires a network round-trip, set
  `loading={pending}` while the request is in flight. The control is
  disabled and a spinner replaces the thumb; releasing the loading state
  reflects the new value.

Anti-pattern to avoid: using Switch when the form needs Submit-time
batched state. Switches imply "applied immediately"; if the change must
go through Save, prefer Checkbox.

## How to use

```tsx
import Switch from '@dt/Switch';

// Controlled toggle
<Switch
  label="Reduced motion"
  checked={reducedMotion}
  onCheckedChange={setReducedMotion}
/>

// With helper text
<Switch
  label="Notifications"
  helperText="Receive email when someone replies."
  checked={emailReplies}
  onCheckedChange={setEmailReplies}
/>

// Async with loading
<Switch
  label="Sync calendar"
  loading={pending}
  checked={synced}
  onCheckedChange={onToggleSync}
/>

// Top-placed label
<Switch label="Dark mode" labelPlacement="top" checked={isDark} onCheckedChange={setIsDark} />
```

Required consumer wiring: nothing. The label is rendered inline by the
component; helper text is also rendered internally. Pass `id` if you
need to associate external `aria-describedby` content beyond the
internal helper.

Theme & forced-colors notes: the on-state surface uses `--color-primary`;
forced-colors mode uses the system's `Highlight` for the on state and
`ButtonText` for the thumb so the contract survives high-contrast.

## When to use

- A binary setting that takes effect immediately (apply-on-toggle).
- A preference toggle in settings, profile, or consent panels.
- A control where "on" / "off" is the right mental model rather than
  "checked" / "unchecked".

## When not to use

- A form field whose value is submitted as part of a larger payload —
  use **Checkbox** so the user has the choose-then-Submit affordance.
- A multi-select group — use **CheckboxGroup**.
- A choose-one selector — use **Radio** / **RadioGroup**.
- A "press to act" button (Start / Stop) — use **Button**.

## Accessibility

- **Semantic:** the underlying element is a `<button role="switch">`. Screen
  readers announce "switch, on/off" rather than "checkbox, checked".
- **Keyboard:** Space and Enter both toggle. Tab follows DOM order. The
  control receives focus directly; the label does not steal focus.
- **State:** `aria-checked` is set to `true` / `false` to match
  `checked`. `aria-disabled` is set when `disabled` or `loading`.
- **Loading:** `aria-busy` is added while `loading`; the click handler
  is suppressed so a second tap during a pending request does not flip
  the visual state before the server confirms.
- **Reduced motion:** the thumb slide transition is suppressed under
  `prefers-reduced-motion: reduce`. State change is still visible — the
  thumb jumps instead of sliding.

## Promotion notes

- Bulk-author target for Honest Beta phase. Reviewed against the cookie

- Stable promotion blockers: a11y-tree snapshots for the four required
  stories, real-browser forced-colors run, documented production consumers.
