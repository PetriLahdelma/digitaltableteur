# Label

**Status:** beta · **Tier:** atom · **Group:** form

Form-field label. Label requires `htmlFor` and uses the native `<label>`
element so the browser handles the focus-and-click association
automatically. Visual affordances cover the `required` marker (an
asterisk plus a screen-reader-only "(required)" word), a `disabled` mute
treatment for greyed-out fields, and an optional `tooltipText` that maps
to the native `title` attribute.

## In use

Every Input, TextArea, Select, Checkbox, and Radio in the contact and
newsletter forms is labelled by a Label atom. The **Example** story
mirrors the canonical input-group composition: `<Label htmlFor> + Input
id + HelperText id`.

Two compositions worth cribbing:

- **Required field with help text.** Pair `<Label required>` with an
  Input and a HelperText. The Label provides the visible required marker
  and the SR text; HelperText carries the explanation via
  `aria-describedby`.
- **Inline tooltip on a long label.** `tooltipText="What this means"` adds
  a native `title` tooltip on hover, useful when labels are abbreviated.
  Note that native tooltips don't fire on touch — keep critical context
  in visible HelperText instead.

Anti-pattern to avoid: wrapping the input inside the Label without
`htmlFor`. The browser does still associate them, but explicit `htmlFor`
is grep-able and survives reordering. Always pass it.

## How to use

```tsx
import Label from '@dt/Label';
import Input from '@dt/TextInput';
import HelperText from '@dt/HelperText';

<Label htmlFor="email" required>Email</Label>
<Input id="email" type="email" aria-describedby="email-hint" />
<HelperText id="email-hint">We never share this address.</HelperText>

// Disabled field
<Label htmlFor="locked" disabled>Locked field</Label>
<Input id="locked" disabled />

// Tooltip on an abbreviated label
<Label htmlFor="vat" tooltipText="Value Added Tax registration number">
  VAT
</Label>
```

Required consumer wiring: the input you label must have a matching `id`.
The Label component does not own the Input — they are sibling atoms by
design so that helper text, validation messages, and form controls all
share the same `id` namespace.

Theme & forced-colors notes: the `disabled` style relies on a muted text
token, but forced-colors mode overrides it with the system's `GrayText`
keyword. The asterisk is rendered with `aria-hidden="true"`; the screen-
reader-only "(required)" carries the semantic.

## When to use

- The visible label for any form input, group, or fieldset legend
  replacement (when wrapping a single input).
- Required-state indication: pair `required` on Label with `required`
  on the input so visual and ARIA states agree.
- Disabled-state visual cue when the input is also disabled.

## When not to use

- A standalone heading above multiple controls — use **Title** with a
  visible `legend`/`fieldset` pair, or `<Title as="div" id>` and an
  `aria-labelledby` on the group.
- Help text below an input — use **HelperText**.
- Validation error messages — those belong to the input's error state and
  the form-level error region, not the Label.

## Accessibility

- **Association:** explicit `htmlFor` is required. The browser handles
  click-to-focus and SR name resolution; nothing custom.
- **Required marker:** the visible `*` is `aria-hidden="true"` so screen
  readers don't say "asterisk". The accompanying `<span className="srOnly">(required)</span>`
  is the announced semantic — clear and translation-friendly.
- **Disabled:** the `disabled` prop only changes the visual class. The
  underlying input must also be `disabled` for the keyboard contract to
  match; Label does not propagate state to siblings.
- **Tooltip:** the native `title` attribute fires on hover with a system
  delay and does not fire on touch. Use HelperText for guidance that
  every user needs.
- **Reduced motion:** Label has no motion to suppress.
