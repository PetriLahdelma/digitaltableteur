# NewsletterWaitlist

**Status:** beta · **Tier:** organism · **Group:** form

Single-purpose email-capture organism for the newsletter waitlist.
NewsletterWaitlist starts as a single Button. Activating it transforms
the surface into a labelled email input plus Submit and Cancel. The
component owns its own loading state, validation, success Modal, and
post-submit reset — consumers pass at most three callbacks
(`onSuccess`, `onError`, `disabled`) and one className.

## In use

Mounted at the bottom of `/` and `/blog` as the primary "stay in
touch" CTA. The transformation pattern (button → input) is what
distinguishes this from a permanent inline form — the visual weight
stays low until the user opts in.

One composition worth cribbing:

- **Default with success modal.** Drop the component in without
  props. It posts to `/api/save-contact` with `type: 'newsletter',
  source: 'waitlist'` and shows a Modal on success. The `onSuccess`
  callback fires with the submitted email so the consumer can
  analytics-track.

Anti-pattern to avoid: mounting two NewsletterWaitlist instances on
the same page. The transformation state is per-instance so both can
expand simultaneously, but the success Modal portal isn't scoped —
two open modals confuse focus management.

## How to use

```tsx
import NewsletterWaitlist from '@dt/NewsletterWaitlist';

// Default
<NewsletterWaitlist />

// With analytics callbacks
<NewsletterWaitlist
  onSuccess={(email) => analytics.track('newsletter_signup', { email })}
  onError={(error) => analytics.trackError('newsletter_signup_failed', error)}
/>

// Disabled during maintenance
<NewsletterWaitlist disabled={isMaintenance} />
```

Required consumer wiring: nothing. The component posts to
`/api/save-contact` directly and surfaces its own validation, loading,
and post-submit states.

Theme & forced-colors notes: the transformation animation is a CSS
opacity / width transition; forced-colors suppresses the visual
shift (the change is instant) but the underlying form behaviour is
unchanged.

## When to use

- Newsletter / waitlist signup on a marketing page.
- Lead capture where the only required field is email.
- Any place a contact form would be overkill and a single button
  too sparse.

## When not to use

- A multi-field form — use **ContactForm**.
- A subscribe-to-tag flow — that's a separate component (planned).
- A login or sign-up flow — those need password handling; build a
  dedicated auth form.
- An RFP or lead-qualification form — too much detail for a single
  email field; route to ContactForm or a dedicated route.

## Accessibility

- **Transformation:** the initial Button announces as "button". After
  activation, the input is rendered with its own `<Label>` — AT users
  hear the label and field state. Focus does not auto-move to the
  input on transformation because focus-stealing without explicit
  intent is a poor AT pattern; users press Tab once after activating
  the button.
- **Validation:** the component runs the same email regex as Inputs
  (`/^[^\s@]+@[^\s@]+\.[^\s@]+$/`) and surfaces the error via the
  Inputs' helper slot.
- **Submit state:** the submit Button's `loading` prop flips
  `aria-busy` during the request. On success the form resets and a
  Modal opens; the Modal's focus trap takes over and restores focus
  on close.
- **Cancel:** Cancel resets to the Button state. Focus does not
  return to the Cancel button (which no longer exists); it returns
  to the Button that started the flow.

## Promotion notes

- Stable promotion blockers: AT-tree snapshots for button / input /
  loading / success-modal states, real-browser forced-colors run,
  documented production consumers (`/` and `/blog` index page).
- Known debt: there is no "already subscribed" affordance. If the
  user has already signed up (server-known), the component still
  shows the Button. A future iteration should accept an
  `isSubscribed` prop and degrade gracefully.
