# WipBadge

**Status:** beta · **Tier:** atom · **Group:** feedback

Storybook-only maturity badge. Non-stable components mount `WipBadge` in their
preview decorators so reviewers can see at a glance whether what they're
looking at is `alpha`, `beta`, or `deprecated` without leaving Storybook. The
badge renders nothing when status is `stable` — promoting a contract is the
visual signal that the badge has earned its way off-screen.

## When to use

- Inside Storybook preview decorators for any component whose contract is not
  `status: "stable"`. The default decorator in `.storybook/preview.tsx` reads
  the contract and mounts the badge automatically; you should rarely need to
  invoke it manually.
- On a documentation page (`variant="docs"`) when you want to keep the maturity
  pill visible inline with prose instead of floated at the viewport corner.

## When not to use

- In production app code. `WipBadge` exists for the catalog. Shipping a maturity
  pill to end users is a UX failure — if the component is not ready, it should
  not be in the production bundle at all.
- For temporary "experimental feature" labels at runtime. Use a domain badge
  (`Badge` component, `variant="warning"`) for that — `WipBadge` is hard-wired
  to the design-system status taxonomy.

## How to use

```tsx
import { WipBadge } from '@dt/WipBadge';

// Canvas mode (Storybook story preview) — fixed bottom-right of the viewport.
<WipBadge status="alpha" />

// Docs mode (Storybook MDX page) — sits inline with the prose.
<WipBadge status="beta" variant="docs" />
```

## In use

The badge is mounted automatically by the Storybook preview decorator for any
component whose contract is not yet `status: "stable"`. The default decorator
reads `<component>.contract.json` and forwards `status` to `<WipBadge />` so the
maturity pill stays in sync with the manifest without manual upkeep. Use the
`docs` variant inside MDX pages when you want the pill to flow with prose, and
the `canvas` variant inside story previews when you want it pinned to the
viewport. The badge sets `data-axe-ignore` so it never participates in the host
component's accessibility evaluation.

The component reads its label from i18n key `storybookWipBadge` so the badge
flips language alongside the rest of the catalog. `role="status"` is set so
assistive tech announces the maturity tier when the badge mounts.

## Anatomy

- **Container.** Fixed-position wrapper (`canvas`) or inline wrapper (`docs`).
  Pointer events are off on the wrapper and on for the badge itself so the
  badge is not click-blocking but is selectable / inspectable.
- **Badge.** `<span role="status">` carrying the localised label plus the
  status in parentheses (e.g. `Work in progress (alpha)`).

## Accessibility

- `role="status"` on the badge → polite announcement on mount.
- The component renders nothing at `status: "stable"`, so screen readers do not
  get a stale "work in progress" announcement on shipped surfaces.
- Forced-colors: the badge inherits `--color-text` and `--color-surface-elevated`
  which both resolve to system colors under forced-colors mode.

## Promotion notes

Promoted to `beta` so the catalog's self-description is itself catalogued and
tested in the matrix/HC runs. The badge is **not** a candidate for `stable`
because promoting it to a public API would imply consumer apps could rely on
it — they cannot. If consumer apps ever need a runtime maturity pill, that
should be a separate component built on `Badge`, not this Storybook-only
chrome.
