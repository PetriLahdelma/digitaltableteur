# HelperText

**Status:** beta · **Tier:** atom · **Group:** form

Semantic help copy that lives beneath a form control. HelperText owns the
paragraph, the optional state icon (`error` / `warning` / `success` /
`info`), and the ARIA wiring consumers route through `aria-describedby`.
When state is `error`, the paragraph becomes a live `alert` region so
validation failures announce immediately.

## In use

Used under every Input, TextArea, Select, and Checkbox in the contact and
newsletter forms — always paired with `aria-describedby` on the input so
screen readers read the help text after the field's accessible name. The
**Example** story shows the canonical neutral + error pairing.

Two compositions worth cribbing:

- **Field hint.** Neutral state with no icon, sitting under an Input.
  Pass an `id` and reference it from the input's `aria-describedby` so
  SR users get the explanation when they focus the field.
- **Validation error.** Set `state="error"`. The paragraph picks up
  `role="alert"`, which the project's tests assert on. The error icon is
  resolved automatically — no need to pass `<Icon name="warning" />`.

Anti-pattern to avoid: putting a validation error message inside the
Label. Errors belong below the field with `role="alert"`; the label is
for the field name.

## How to use

```tsx
import HelperText from '@dt/HelperText';

// Neutral hint
<HelperText id="email-hint">We never share this address.</HelperText>

// Error message (auto-announces via role="alert")
<HelperText id="email-error" state="error">
  Enter a valid email address.
</HelperText>

// Wire to an input
<Input id="email" aria-describedby="email-hint email-error" />
```

Required consumer wiring: the field whose help this describes must
reference the HelperText's `id` via `aria-describedby`. Without the
association, the help text is visually present but not announced.

Theme & forced-colors notes: state colours come from the same semantic
token family Badge uses, so the visual contract stays consistent across
the form atoms. The error icon flips to the system's `Mark` colour in
forced-colors mode.

## When to use

- A field hint that explains what to enter (`We never share this`).
- A validation error message tied to a specific field.
- A non-blocking warning or success indicator under a field.

## When not to use

- A page-level alert that's not field-scoped — use **AlertBanner**.
- A toast notification for a transient event — use **Toast**.
- The required marker on a Label — that lives on **Label** itself.
- A non-form context — HelperText is intentionally scoped to field help;
  inline body copy belongs in **Text**.

## Accessibility

- **Field association:** consumers must wire `aria-describedby` to the
  HelperText's `id`. The component does not own the input — that's a
  sibling-atom design choice for clarity.
- **Error live region:** when `state="error"` the paragraph emits
  `role="alert"` so screen readers announce the error as soon as it
  renders. The icon is `aria-hidden`; the visible text is the semantic.
- **Other states:** `warning`, `success`, `info` are decorative — they
  use the semantic icon for visual scanning but do not create a live
  region. Reserve announcements for actual errors.
- **Reduced motion:** HelperText has no motion to suppress.

## Promotion notes

- Bulk-author target for Honest Beta phase. Reviewed against the contact
  and newsletter form fields; the error path is the most-tested surface.
- Stable promotion blockers: a11y-tree snapshots for the four required
  stories, real-browser forced-colors run, documented production consumers.
- Known debt: there is no `assertive` live-region option. If a multi-step
  flow surfaces an error that demands interruption, escalate to a Toast
  (which carries the right live-region semantic) rather than overriding
  HelperText's politeness.
