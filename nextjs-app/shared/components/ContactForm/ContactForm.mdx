# ContactForm

**Status:** beta · **Tier:** organism · **Group:** form

The shipping contact form on `/contact`. ContactForm orchestrates
seven inputs (Inputs × name, email; PhoneInput; Select × interest and
hear-about; TextArea × message; CheckboxGroup × channels), an optional
FileUpload, a loading Button for submit, plus Toast and Modal
for post-submit feedback. A honeypot field (`honeypot`, hidden via
`tabIndex={-1}` and `aria-hidden`) catches non-human submissions, and
the email field runs typo suggestions before submission is allowed.

## In use

The single canonical consumer is `app/contact/page.tsx`, which mounts
ContactForm as the bottom-of-page CTA on the contact route. The
component takes no props (`Record<string, never>`) because its
behaviour is tightly bound to the `/api/contact` endpoint and the
i18n keys under `contactForm.*`.

Two compositions worth cribbing:

- **Attachment with size validation.** The internal FileUpload uses
  `CONTACT_ATTACHMENT_MAX_BYTES` for the size limit. Files above
  `CONTACT_EMAIL_ATTACHMENT_LIMIT_BYTES` are still accepted but the
  user sees a warning that the file is too large to email (a Resend
  limitation) and will be uploaded to S3 instead.
- **Honeypot + reCAPTCHA-free spam control.** Bots that fill every
  field will trip the honeypot. The submit handler calls
  `reportContactHoneypot()` for telemetry, then silently no-ops (so
  the bot thinks the submission succeeded).

Anti-pattern to avoid: forking ContactForm to add a "company" field
or change the layout. The form is intentionally a single fixed
composition — variant work should happen in **patterns** that
compose smaller atoms. Adding a second form variant here breaks the
analytics, i18n, and rate-limiting assumptions baked into
`/api/contact`.

## How to use

```tsx
import ContactForm from '@dt/ContactForm';

// Drop into a page
<section aria-labelledby="contact-heading">
  <Title id="contact-heading">{t('contactPageHeading')}</Title>
  <ContactForm />
</section>
```

Required consumer wiring: the parent must surround the form with a
heading element for accessibility and provide the locale via the
i18n provider already mounted at the layout level. The component
reads its translations from the `contactForm.*` namespace plus a
handful of shared validation keys.

Theme & forced-colors notes: every child component carries its own
forced-colors contract; ContactForm adds no extra colour wiring. The
submit button uses `Button`'s `loading` prop so the loading state has
the right ARIA wiring even on slow networks.

## When to use

- The contact route. There is no other consumer — that's the point.
- A landing page where the contact form is the primary CTA (mount
  ContactForm directly; don't rebuild it).

## When not to use

- A newsletter signup — use **NewsletterWaitlist** (single email
  field, very different visual idiom).
- A short feedback form (one or two fields) — compose Inputs +
  Button directly.
- A multi-step flow (onboarding, checkout) — ContactForm is a
  single submit. For multi-step, build a route per step.

## Accessibility

- **Field labelling:** every field is wrapped in its own labelled
  child (Inputs / Select / PhoneInput / TextArea / CheckboxGroup /
  FileUpload). The heading above ContactForm is the consumer's
  responsibility — the form does not own its own `<h1>`.
- **Validation:** email validation runs through
  `validateContactEmail` (server-aligned regex + typo suggestion).
  Invalid emails block submission and surface the error in the
  Inputs' helper slot.
- **Honeypot:** the hidden `honeypot` Inputs uses
  `aria-hidden="true"` and `tabIndex={-1}`. The field has a label
  but the label is hidden — AT users skip it; bots fill it.
- **Submit state:** the submit Button's `loading` prop flips
  `aria-busy` during submission and prevents double-submit by
  disabling itself. The form is also rate-limited at `/api/contact`
  (1 req / 30s per IP).
- **Post-submit:** success surfaces in a Modal (focus moves to the
  modal, restores on close); errors surface in an inline Toast (no
  focus disruption).

## Promotion notes

- ContactForm is the highest-stakes form in the system because every
  inbound lead goes through it. Stable promotion is gated on:
  - AT-tree snapshots for the four required stories (empty / partial
    / error / success).
  - Real-browser forced-colors verification of every child field.
  - Documented production consumer (`/contact` is the canonical, sole
    consumer).
  - Manual screen-reader pass through submission flow — captured in
    `ContactForm.contract.json#a11y.screenReaderNote`.
- Known debt: there is no "save draft" / restore-on-reload behaviour.
  The team has decided this is the right call for contact forms —
  draft state breeds stale submissions — but a future "long-form RFP"
  variant might need it.
