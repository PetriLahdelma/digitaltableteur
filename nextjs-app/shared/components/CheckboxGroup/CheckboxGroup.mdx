# CheckboxGroup

**Status:** beta · **Tier:** molecule · **Group:** form

Group of related checkboxes with an optional "select all" master.
CheckboxGroup is the canonical multi-select pattern in the system —
each option submits independently as part of the form payload, and the
master checkbox keeps `indeterminate` state in sync when a subset is
selected. Driven by an `options` array of `{ label, value }`; the
callback fires with the array of selected values.

## In use

Used in the contact form (multi-channel preferences: email / phone /
LinkedIn) and on the legal form for cookie category opt-ins. The
GDPR-data-deletion flow uses a single CheckboxGroup to pick which
categories of data to remove.

Two compositions worth cribbing:

- **With master select-all.** Default. The master row shows
  `indeterminate` when some — but not all — options are checked, and
  toggles everything when activated. Useful for long lists where the
  user wants to opt in to most or all.
- **Without master.** Pass `showMasterCheckbox={false}` for short lists
  where the master adds clutter. Each option still drives `onChange`
  with the cumulative selection.

Anti-pattern to avoid: passing options whose `value` is non-unique.
The internal state uses `value` as the identity key; duplicates break
toggle tracking silently.

## How to use

```tsx
import CheckboxGroup from '@dt/CheckboxGroup';

// With master
<CheckboxGroup
  id="contact-channels"
  label={t('contactPreferredChannels')}
  masterLabel={t('contactAllChannels')}
  options={[
    { label: t('channelEmail'), value: 'email' },
    { label: t('channelPhone'), value: 'phone' },
    { label: t('channelLinkedIn'), value: 'linkedin' },
  ]}
  defaultSelected={['email']}
  onChange={setChannels}
/>

// Without master
<CheckboxGroup
  id="cookie-categories"
  label={t('cookieCategories')}
  options={cookieCategoryOptions}
  showMasterCheckbox={false}
  onChange={setEnabledCategories}
/>
```

Required consumer wiring: nothing. The component owns the array of
checked states; the consumer receives the resolved values via
`onChange`. The `id` prop is used as the prefix for child checkbox
ids — pass a stable one per instance.

Theme & forced-colors notes: each child Checkbox follows its own
forced-colors contract; the group adds no extra colour wiring. The
group label uses `<GroupLabel>` which renders as `<legend>`-style
text bound to the master (when present) or to the first option.

## When to use

- Multi-select where each value submits independently
  ("Email me about: design / engineering / business").
- Opt-in flows (cookie categories, GDPR preferences).
- Filter UIs that combine multiple toggles ("Show: drafts / published
  / archived").

## When not to use

- Single-select — use **Select** or **RadioGroup**.
- A single binary toggle — use **Checkbox** directly.
- A long list (>~15 items) — switch to a multi-select chip pattern;
  the visual breaks down with too many rows.
- A switch-style "apply immediately" toggle — use **Switch**.

## Accessibility

- **Labelling:** the group is wrapped in a `<GroupLabel>` that the
  master checkbox (or first option) `htmlFor`-links to. Screen
  readers announce the group label before each option.
- **Master state:** the master checkbox's `aria-checked` is `true` /
  `false` / `mixed` (indeterminate). AT users hear "mixed" when only
  some options are selected, which matches WAI-ARIA tri-state semantics.
- **Keyboard:** Tab moves through master + each option in DOM order.
  Space toggles the focused checkbox. There is no roving tabindex —
  every checkbox is in the tab sequence, matching native form
  expectations.
- **Reduced motion:** no animation is applied on toggle; visual state
  changes are instant.
- **Translation:** the master label translation key is
  `contactAll`. The component falls back to "All" if the key isn't
  resolved (e.g. in tests without i18n initialised). Pass
  `masterLabel` to override per-instance.

## Promotion notes

- Stable promotion blockers: AT-tree snapshots for the master /
  indeterminate / none-selected states, real-browser forced-colors
  run, documented production consumers (contact form channels is the
  canonical use).
- Known debt: there is no validation hook for "at least one selected".
  Consumers handle that in their form layer; flagged for a `required`
