# Accordion

**Status:** beta · **Tier:** molecule · **Group:** structure

Single-expansion accordion. Each section renders a `<button>` trigger
with `aria-expanded` / `aria-controls` wired to a `<div role="region">`
panel labelled by the trigger. Opening any item collapses the previously
open one — single-expansion is intentional. Pass an array of
`{ id, title, content }` items and an optional `defaultOpenId` to set
the initially open section.

## In use

Used by the FAQ section on `/contact` and the "what's included"
expandables on the pricing surface. Sub-page navigation does **not** use
Accordion — that pattern lives in `<NavMenuList />`.

One composition worth cribbing:

- **FAQ with rich content.** The `content` slot accepts any node, so
  paragraphs, lists, code blocks, and even other components fit inside.
  Keep the answer short enough that the keyboard user doesn't have to
  scroll vertically inside a single open panel.

Anti-pattern to avoid: making accordion the *only* affordance for content
that must be scannable. Search engines and AT users benefit from a flat
H2 / H3 outline; gate accordion to truly secondary content.

## How to use

```tsx
import Accordion from '@dt/Accordion';

<Accordion
  defaultOpenId="pricing"
  items={[
    {
      id: 'pricing',
      title: 'How is the engagement priced?',
      content: <p>Sprints are fixed-fee. Retainers are weekly.</p>,
    },
    {
      id: 'timeline',
      title: 'How long does a typical sprint take?',
      content: <p>Five working days from kickoff to handover.</p>,
    },
  ]}
/>
```

Required consumer wiring: nothing. The trigger and panel `id`s are derived
from `item.id`, so consumer code must guarantee `item.id` is unique per
accordion instance.

Theme & forced-colors notes: the open-state caret rotation uses CSS
transforms only; forced-colors keeps the system caret. The panel border
falls back to `ButtonBorder` in forced-colors mode so the open/closed
distinction survives without colour.

## When to use

- Secondary content that doesn't warrant a separate page (FAQ, "details").
- Long-form content where the user wants to scan headings first.
- Settings panels where related groups can hide until needed.

## When not to use

- Primary navigation — use **NavMenuList**.
- Step-by-step flows where order matters — use **Tabs** or a stepper.
- Disclosure of a single block of content — use a `<details>` element
  directly; Accordion's group machinery is overkill for one item.
- Mobile navigation — use **patterns/MobileDrawer**.

## Accessibility

- **Roles:** each item is a `<button aria-expanded>` paired with a
  `<div role="region" aria-labelledby={trigger}>`. The pattern follows
  the ARIA Authoring Practices Guide for disclosure widgets.
- **Keyboard:** Enter and Space toggle the focused item. Tab order
  follows DOM order. There is no roving tabindex — every trigger is in
  the tab sequence (the APG explicitly permits this for disclosure
  groups).
- **State:** `aria-expanded` flips per click; `hidden` is applied to
  the panel so the contents are removed from the AT tree when closed.
  Screen readers announce "collapsed" / "expanded" on each toggle.
- **Single-expansion semantics:** there is no `aria-multiselectable`
  because each disclosure is independent — toggling one collapses the
  rest as a side-effect, not as a group constraint.

## Promotion notes

- Stable promotion blockers: AT-tree snapshots for the closed-and-open
  story, real-browser forced-colors run, and documented production
  consumers (the FAQ section is the leading candidate).
- Known debt: there is no `mode="multi"` for multi-expansion. Adding it
  would change the keyboard contract slightly (`aria-multiselectable` on
  the wrapper) and is deferred until a real consumer needs it.
