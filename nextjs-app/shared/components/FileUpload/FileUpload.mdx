# FileUpload

**Status:** beta · **Tier:** molecule · **Group:** form

File-attachment control with a hidden native input, a visible
read-only Inputs field showing the file summary, a Browse button, and
an optional Clear button. FileUpload runs client-side size validation
(`maxSizeInBytes`) and rejects oversize files with a translated error
message. The hidden native input keeps platform UX (mobile camera,
drag from Finder/Explorer); the visible field exists so the user can
see what they picked and clear it without juggling the native input.

## In use

The contact form uses FileUpload for the optional attachment slot
(brief PDF, sketch, screenshot). The CV download flow does **not** —
it uses a server-side password verification instead. No other
production flow ships file upload yet.

Two compositions worth cribbing:

- **With size validation.** Pass `maxSizeInBytes` and a translated
  `sizeErrorMessage` for the user-facing error. The component
  rejects the file on the spot (it never reaches `onFileChange`),
  resets the native input value, and surfaces the error via the
  internal `HelperText`.
- **Clear-after-select.** Pass `clearButtonLabel` to render the clear
  action next to Browse. Useful when the form lets the user "change
  their mind" without uploading something new first.

Anti-pattern to avoid: relying on `accept` for security validation.
The `accept` attribute is a hint to the file picker — users can
still pick anything from "All files". Validate type server-side.

## How to use

```tsx
import FileUpload from '@dt/FileUpload';

<FileUpload
  label={t('contactAttachmentLabel')}
  placeholder={t('contactAttachmentPlaceholder')}
  helperText={t('contactAttachmentHelper')}
  uploadButtonLabel={t('contactAttachmentBrowse')}
  clearButtonLabel={t('contactAttachmentClear')}
  accept=".pdf,.png,.jpg,.jpeg"
  maxSizeInBytes={CONTACT_ATTACHMENT_MAX_BYTES}
  sizeErrorMessage={t('contactAttachmentTooLarge', {
    max: maxSizeMB,
  })}
  value={attachmentFile}
  onFileChange={setAttachmentFile}
/>
```

Required consumer wiring: the consumer owns the `File | null` state
and receives `onFileChange` updates. The component is controlled —
passing `value` updates the visible field. If the consumer doesn't
manage the value at all, omit `value` and rely on internal state
plus the `onFileChange` callback.

Theme & forced-colors notes: the hidden input has `aria-hidden="true"`
and `tabIndex={-1}`; the visible Inputs field is the focusable
surface. Browse and Clear are tertiary / secondary Buttons inheriting
their own theme tokens.

## When to use

- Single-file attachment in a form (PDF, image, document).
- Optional supporting material the user can attach but doesn't have
  to (contact form attachment is the canonical use).
- Avatar / profile picture upload with client-side size limits.

## When not to use

- Multi-file upload — the component is single-file. Multi-file is
  not yet on the roadmap; raise it as a need when one arises.
- Drag-and-drop dropzone — separate pattern, not yet built.
- File download — that's just a Link with a `download` attribute.
- Server-side image processing — handle that in the API route; the
  component only handles selection and size validation.

## Accessibility

- **Native input:** the file `<input>` is `aria-hidden`, `tabIndex={-1}`,
  and styled `display: none`. It exists only to trigger the platform
  picker; users never reach it directly.
- **Visible field:** the `Inputs` displays the file summary
  (name + size). It's `readOnly`, with a click handler that opens the
  picker — so clicking the field has the same effect as the Browse
  button.
- **Buttons:** Browse is a secondary Button; Clear is a tertiary
  Button shown only when a file is selected. Both are in the tab
  sequence; the visible field is also focusable but read-only.
- **Error state:** size-validation errors surface via the internal
  `HelperText state="error"`. The error replaces (rather than
  appends to) the helper text. `aria-describedby` from the Inputs
  points to the helper id so the AT user hears the error on field
  focus.
- **Translations:** `uploadButtonLabel`, `clearButtonLabel`,
  `sizeErrorMessage`, and the field label are all consumer-provided
  strings. The component does not i18n itself — pass translated
  copy.

## Promotion notes

- Stable promotion blockers: AT-tree snapshots for default /
  selected / oversize-error states, real-browser forced-colors run,
  documented production consumer (contact form attachment is the
  shipping use).
- Known debt: no progress indicator for large files. Upload
  progress lives in the network layer (fetch with body progress
  events is non-trivial); flagged for a future v2.
