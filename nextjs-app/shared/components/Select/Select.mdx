# Select

**Status:** beta · **Tier:** atom · **Group:** form

Labelled native `<select>` with size variants, error state, and a
helper-text slot. Select uses the native control on purpose — system
keyboard and screen-reader support is unmatched by any JS combobox.
Custom-rendered option lists are out of scope; if a consumer needs
search-inside-options, that's a separate component (planned).

## In use

Used in the contact form (interest selector, "how did you hear about
us" selector) and in the chat widget's preference panel. The blog
filter on `/blog` uses Select for the tag picker.

Two compositions worth cribbing:

- **Controlled with options array.** Pass `options={[{ value, label }]}`
  and the component renders the option list internally. Use
  `onValueChange={setValue}` and pass `value` for controlled mode.
- **Hand-rendered options.** Pass `children` (an array of
  `<SelectOption>` or native `<option>` elements) when the option
  list needs grouping (`<optgroup>`) or async injection. The
  `options` prop is ignored when `children` is present.

Anti-pattern to avoid: rendering a Select with a single option. If
there's no real choice, the field shouldn't exist — either remove it
or surface the value as static **Text**.

## How to use

```tsx
import Select from '@dt/Select';

// Controlled with options
<Select
  label={t('contactInterest')}
  options={[
    { value: 'sprint', label: t('contactInterestSprint') },
    { value: 'retainer', label: t('contactInterestRetainer') },
    { value: 'advisory', label: t('contactInterestAdvisory') },
  ]}
  value={interest}
  onValueChange={setInterest}
  helperText={t('contactInterestHelper')}
/>

// With error state
<Select
  label={t('contactHearAbout')}
  options={hearAboutOptions}
  value={hearAbout}
  onValueChange={setHearAbout}
  error={errors.hearAbout}
/>

// With native optgroup
<Select label={t('blogTag')} value={tag} onValueChange={setTag}>
  <optgroup label={t('blogTagDesign')}>
    <SelectOption value="systems" label={t('tagSystems')} />
    <SelectOption value="research" label={t('tagResearch')} />
  </optgroup>
  <optgroup label={t('blogTagEngineering')}>
    <SelectOption value="storybook" label={t('tagStorybook')} />
    <SelectOption value="tokens" label={t('tagTokens')} />
  </optgroup>
</Select>
```

Required consumer wiring: nothing. The label renders via the system
`Label` primitive and is associated to the `<select>` via `htmlFor` /
`id`. Helper and error text render via `HelperText`.

Theme & forced-colors notes: the chevron icon is rendered via the
system `Icon` and positioned absolutely; in forced-colors the system
draws its own chevron, so the custom one is hidden under `Canvas`. The
contract still holds because the native select's affordance is intact.

## When to use

- A single-value choice from a small (≤ ~15) list of static options.
- A form field whose value submits with the rest of the form.
- A picker on mobile — the native sheet UX is superior to any custom
  control.

## When not to use

- Multi-select — use **CheckboxGroup** or a tag-input pattern.
- Search-inside-options — out of scope for this component (consumer
  should build a combobox or ask for one to be added).
- A toggle between two states — use **Switch**.
- Inline picker that should look like text — use a custom
  inline-edit pattern.

## Accessibility

- **Native semantics:** the underlying `<select>` carries every
  keyboard, screen-reader, and forced-colors behaviour for free.
  ArrowUp / ArrowDown moves the highlighted option; Enter / Space
  opens the list on most platforms; type-ahead jumps to the first
  matching option.
- **Label:** the `<Label>` primitive is mounted with `htmlFor` set to
  the select id (provided via `id` prop or `useId()` fallback). The
  label is *not* announced via `aria-labelledby` — `htmlFor` is the
  correct primitive for native form controls.
- **Error state:** `error` enables `aria-invalid` and shows the error
  via `<HelperText state="error">`. The helper text and error text are
  mutually exclusive — error wins.
- **Disabled:** `isDisabled` (or the deprecated `disabled`) sets the
  native disabled state. Disabled options inside the list use the
  per-option `isDisabled` (deprecated `disabled` is still honoured).

## Promotion notes

- Stable promotion blockers: AT-tree snapshots for default / error /
  disabled, real-browser forced-colors run, and documented production
  consumers (contact form is the canonical use).
- Known debt: the `onChange` and per-option `disabled` props still emit
  deprecation warnings. Removal scheduled in v2.0.0 after consumers
  migrate to `onValueChange` and `isDisabled`.
